# Emby 预览片下载业务流程

状态：统一落地方案  
适用范围：仅 Emby 版本  
最后整理：2026-08-31

## 1. 方案目标

插件通过一套统一的业务检测流程处理预览片下载：

- 新电影完成 MetaTube 元数据刮削后，自动检查并补充本地预览片；
- 用户手动刷新电影元数据后，自动重新检查本地预览片；
- 用户运行“Generate Trailers”计划任务时，进行 Emby 库全量检查；
- 所有入口都先检查元数据和本地文件，只有确实缺少预览片时才进入下载；
- 本地已经存在预览片时不重复下载、不覆盖现有文件。

自动触发和全量检查不是两套业务逻辑。它们只是候选电影的来源不同，之后必须经过完全相同的检测流程和同一条下载队列。

本方案只负责“把预览片文件下载到正确的位置”。文件落盘后由 Emby 自己的库扫描识别成本地预览片，插件不主动触发刷新。

## 2. 当前实现存在的问题

当前 `GenerateTrailersTask` 是唯一入口，只能靠计划任务触发，且存在以下问题：

1. **目标文件名依赖 `item.Name`**：现在用 `item.Name.Split().First()` 生成文件名。本仓库启用了标题翻译，`item.Name` 形如 `SONE-123 中文标题`，翻译结果或用户手改标题都会改变它，导致“精确路径已存在”的判断失效，同一部电影被重复下载成多个文件。
2. **HLS 地址会产出假的 mp4**：`MovieProvider` 在 `preview_video_url` 为空时回退 `preview_video_hls_url`，而下载器是单次 GET 直写文件。`.m3u8` 播放列表会被“完整下载”，长度校验通过，重命名成 `xxx-trailer.mp4`。这个假文件会让之后所有检查都判定“已存在”，闭环永久卡死且用户无法察觉。
3. **本地存在性判断过窄**：只检查插件自己算出的那一个精确路径，用户自己放的预览片、Emby 认可的其他命名都识别不到。
4. **超时是总时长而非空闲时长**：`DownloadTimeoutSeconds = 300` 覆盖整个下载过程，稍大的文件在慢速源上必然被砍断，而且三次重试会被同样地砍三次。
5. **没有刮削完成后的自动触发**：新电影入库刮削完必须等下一次计划任务才会补预览片。

## 3. MetaTube 预览片元数据来源

Emby 刮削电影元数据时，插件按以下顺序取得预览片信息：

1. 从 Emby 的 `MovieInfo` 读取 MetaTube ProviderId；
2. ProviderId 不完整时，先搜索影片并选择结果；
3. 调用 MetaTube `GetMovieInfoAsync(...)` 获取完整电影元数据；
4. 从返回数据读取 `preview_video_url`；
5. **只有 `preview_video_url` 非空时**才写入 `ProviderIds["TrailerUrl"]`；
6. `MovieProvider` 将 `MetadataResult<Movie>` 返回给 Emby，由 Emby 合并并保存到媒体库。

### 3.1 不再使用 HLS 回退

`preview_video_hls_url` 不再作为回退写入 `TrailerUrl`。

原因：当前下载器是单次 HTTP GET 直接写文件，无法处理 m3u8 播放列表。写入 HLS 地址会稳定产出一个内容是播放列表文本、扩展名却是 `.mp4` 的假文件，破坏“正式文件出现即代表下载成功”这一前提。

若将来接入 ffmpeg 具备 HLS 拉流能力，再单独评估恢复该回退。

`MovieProvider` 返回的 `MetadataResult<Movie>.Item` 是交给 Emby 合并的中间对象，不是检测流程的输入。预览片检测必须等 Emby 保存完成后，用电影的 `InternalId` 从 `ILibraryManager` 重新读取当前记录，不能直接在 `GetMetadata()` 内下载。

## 4. 触发时机

### 4.1 两个入口

#### 入口一：元数据保存后自动检查

插件通过 `IServerEntryPoint` 在启动时订阅 `ILibraryManager.ItemUpdated`，在 `Dispose()` 中退订。

选择 `ItemUpdated` 而不是 `ItemAdded`：新电影入库时先触发 `ItemAdded`，此时 MetaTube 元数据和 `TrailerUrl` 尚未写入；刮削完成后 Emby 调用 `UpdateItem` 才触发 `ItemUpdated`，那时数据才是完整的。

自动检查覆盖：

- 新电影首次完成 MetaTube 刮削；
- 原来没有预览片 URL，刷新后取得 URL；
- 原来已有预览片 URL，用户再次刷新元数据；
- 用户删除本地预览片后再次刷新元数据。

#### 入口二：计划任务全量检查

用户运行“Generate Trailers”计划任务，查询全部带 MetaTube ProviderId 的 Emby 电影。

该任务**不设置默认触发器**，`GetDefaultTriggers()` 返回空序列。任务只在用户手动运行时执行，需要定时的用户自行在 Emby UI 中添加触发器。

> 注意：Emby 把每个任务的触发器持久化在自己的配置中。已经安装过旧版本的用户，其“每天 1:00”触发器已写入 Emby 配置，删除代码里的默认值不会清除它，需要用户在 UI 中手动移除。全新安装则是无触发器状态。

### 4.2 事件过滤

`ItemUpdated` 触发频繁，事件处理器必须先做三层过滤，全部通过才进入后续流程：

1. **按更新原因过滤**：`ItemChangeEventArgs.UpdateReason` 必须包含 `MetadataDownload`、`MetadataEdit`、`MetadataImport` 三者之一。排除 `ImageUpdate` 和 `None`，避免图片保存等无关更新反复触发文件系统检查。
2. **按类型过滤**：`e.Item is Movie movie && movie.ExtraType == null`。Emby 中 `Trailer` 与 `Movie` 同为 `Video` 的子类，类型判断已能排除 Trailer 实体；追加 `ExtraType == null` 是为了排除被解析成 `Movie` 的附加内容——下载完成的预览片被 Emby 扫入库后本身也是一个 item，也会触发 `ItemUpdated`。
3. **按可用性过滤**：排除 `IsVirtualItem` 为真、`IsFileProtocol` 为假的项，它们没有可用的本地路径。

### 4.3 串行队列

事件处理器**不允许等待锁、不允许做文件 IO、不允许执行下载**。它只做过滤、去重入队，然后立即返回。

原因：`ItemUpdated` 是同步事件。在回调里等待一把可能持有数分钟的下载锁会阻塞 Emby 的库更新管道；而改成“锁忙就跳过”则会在批量入库时丢任务——用户一次放入 10 部新片，第一部占住锁下载期间，其余 9 部的事件全部被丢弃，“刮削完自动下载”在最常见场景下直接失效。

统一使用一条去重队列：

- 队列元素是电影的 `InternalId`（`long`）；
- 入队前用集合去重，同一 `InternalId` 在队列中只保留一份，重复事件自动合并；
- 单个后台消费者顺序取出并执行统一检测流程；
- 两个入口调用同一个 `Enqueue(long internalId)`，没有第二条路径。

队列本身就是串行器，因此**不需要任何全局执行锁**，也不需要针对电影、目标文件或临时文件设置额外的锁。插件内任意时刻最多有一个预览片检查或下载在执行。

#### 计划任务的两阶段与进度

计划任务分两个阶段执行，目的是让进度条的分母是“真正需要下载的数量”而不是全库总数：

1. **预检阶段**：查询全部带 MetaTube ProviderId 的电影，对每部调用第 5 节的检测函数 `Check(internalId)`，得到需要下载的候选集合 N。这一阶段不上报百分比，只在结束时记录 `本次待下载 N 部`。
2. **下载阶段**：只把这 N 部入队，等待处理完成。进度 = 已完成数 / N × 100，每完成一部前进一格。失败也计入“已完成”，进度不会卡住。

分母必须是 N 而不是全库总数：五千部片里四千九百多部会被秒跳过，按总数算的话进度条会瞬间冲到 99% 再卡住数小时，比不显示更糟。

计划任务与自动检查排在同一条队列里，不存在互斥失败。

任务结束时必须输出汇总：`待下载 N，成功 X，失败 Y`，并逐条列出失败的电影名与失败原因，用户据此决定是否再跑一次。

#### 取消

用户在 Emby 中停止“Generate Trailers”任务时：清空队列中尚未开始的项，并取消当前正在进行的下载。被丢弃的自动入队项不做补偿，下次刮削或下次全量检查会重新覆盖到。

#### 重启

队列在内存中，Emby 重启后丢失。未处理完的项不持久化、不在启动时扫描恢复，由用户下次运行全量检查补齐。

## 5. 统一检测流程

检测流程实现为一个**无副作用的纯函数**：

```text
TrailerCheckResult Check(long internalId)
    → { NeedDownload, TargetPath, SkipReason }
```

它只读取数据库记录和文件系统，不写文件、不删文件、不下载。两个调用点：

- **计划任务预检阶段**：对全库逐个调用，统计出待下载数 N；
- **队列消费者出队时**：再调用一次，为真才进入下载。

同一个函数两处调用，不是两套逻辑。消费者出队时重新 `Check()` 不是浪费——预检与实际下载之间可能相隔数小时，本地文件状态早已可能改变，这次复查本来就是必需的。`Check()` 只做数次 `File.Exists` 与目录枚举，重复调用的开销可以忽略。

每一次 `Check(internalId)` 必须严格按以下顺序检测。

### 第一步：功能是否启用

检查 `EnableTrailers`：未启用则结束。

### 第二步：读取并确认电影记录

调用 `ILibraryManager.GetItemById(internalId)` 重新读取当前已持久化的记录，并确认结果是 `Movie`：

- 记录不存在或不是电影：结束；
- 是电影：继续。

必须重新读取，不能复用事件参数里的对象或元数据提供器返回的中间对象。该检查同时排除了入队后被删除的电影。

### 第三步：MetaTube 元数据是否完整

同时检查：

- 电影具有有效的 MetaTube ProviderId；
- `TrailerUrl` 非空。

任一条件不满足即结束，不下载。

### 第四步：是否被用户忽略

检查 `电影目录/trailers/.ignore` 是否存在，存在则结束。

`.ignore` 是**目录级**开关，作用于该目录下的所有电影，这是有意设计。

### 第五步：本地是否已经存在预览片

本地文件是是否需要下载的唯一依据。只做文件系统检查，不查询 Emby 数据库。

> 不使用 `LocalTrailerIds` / `GetExtras()`：新下载的文件在 Emby 重新扫描之前不会出现在数据库里，这类查询永远滞后于文件系统，无法作为判断依据，只会引入不一致。

**有效预览片文件**的定义：

- 扩展名属于视频白名单：`.mp4` `.mkv` `.avi` `.wmv` `.mov` `.m4v` `.flv` `.ts` `.webm` `.mpg` `.mpeg` `.rmvb` `.asf` `.m2ts`；
- 文件长度大于 0 字节；
- 不是 `.tmp` 文件，不是隐藏文件，不是 macOS 的 `._` 前缀文件。

检查两处，命中任意一处即视为已存在：

1. `电影目录/trailers/` 下存在任意有效预览片文件；
2. `电影目录/` 下存在任意 `*-trailer.<视频扩展名>` 的有效文件（Emby 的后缀规则，覆盖 `{主视频文件名}-trailer.ext` 和 `movie-trailer.ext`）。

Emby 支持的本地预览片结构见官方说明：<https://emby.media/support/articles/Trailers.html>

判断规则：

- 已存在：结束，不下载、不覆盖，即使远程 URL 发生变化也不更新；
- 全部不存在：继续；
- **一个目录只保留一个预览片**。同一目录下如有多部电影（通常是同一部片的不同版本），共用一个预览片是期望行为，不为每部单独下载。因此规则 1 不做文件名匹配，目录下有任意有效预览片就算已满足。

#### 零字节文件的处理

规则 1、2 已经把 0 字节文件排除在“有效”之外，因此它不阻止下载，`Check()` 直接把它当作“不存在”。

`Check()` 不删除任何文件。清理动作放在第七步落盘前执行，且范围严格限定：**只有当 0 字节文件恰好是本次计算出的目标路径时才删除它**，其余任何文件一律不动。用户放置的文件即使是 0 字节也不删除，只是不算作有效预览片。

必须删除而不是忽略：第七步用 `File.Move(overwrite: false)` 落盘，目标位置若残留一个 0 字节文件会导致移动直接失败。

### 第六步：计算目标路径

目标目录固定为 `电影目录/trailers/`。

目标文件名按以下优先级取得基名，加上 `-trailer.mp4` 后缀：

1. `File.Exists(item.Path)` 成立时，取 `Path.GetFileNameWithoutExtension(item.Path)`；
2. 否则（`item.Path` 是目录或不存在）取该目录名；
3. 仍然取不到时，回退 `item.Name.Split().First()`。

选择原视频文件名而不是 `item.Name`：媒体库中的原始文件名固定是番号（如 `SONE-123.mp4`），不受标题翻译和用户改名影响，是稳定标识。`item.Name` 形如 `SONE-123 中文标题`，会随翻译结果和用户编辑变化，是当前重复下载的根因。

最终路径形如：

```text
电影目录/trailers/SONE-123-trailer.mp4
```

#### 旧文件兼容

旧版本按 `{item.Name 第一个词}-trailer.mp4` 生成的文件，只要位于 `trailers/` 目录且有效，就会被第五步规则 1 识别为“已存在”，不会重复下载。插件不重命名、不迁移这些旧文件。

### 第七步：执行下载

1. 创建 `trailers` 目录；
2. 校验 URL：非法 URL、以 `.m3u8` 结尾的地址直接失败，不重试；
3. 发起请求，`HttpCompletionOption.ResponseHeadersRead`；
4. 校验响应头：状态码非 2xx 失败；`Content-Type` 为 `application/vnd.apple.mpegurl` 或 `application/x-mpegurl` 时判定为 HLS，直接失败且不重试；
5. 以 `FileMode.Create` 打开固定的 `.tmp` 路径。如果该目标存在以前异常终止留下的 `.tmp`，本次下载直接覆盖；
6. 流式写入 `.tmp`，**空闲超时**由计时器控制：连续 N 秒没有读到任何数据才判定超时，而不是限制下载总时长；
7. 下载完成后校验：`Content-Length` 已知时字节数必须一致；文件长度必须大于 0；
8. 正式落盘前再次执行 `Check()`。若用户在下载期间放入了有效预览片，删除本次 `.tmp` 并结束，不覆盖用户文件；
9. 目标路径若存在 0 字节文件，此时删除它，否则下一步的 `overwrite: false` 会失败；
10. 以 `File.Move(temp, final, overwrite: false)` 移动为正式文件。同目录内的重命名是原子操作，正式文件要么完整出现、要么完全不出现；
11. 失败或取消时，在 `finally` 中删除本次 `.tmp`；
12. 有限次重试，失败之间有短暂退避；用户主动取消、URL 非法、判定为 HLS 时不重试。

### 关于 `.tmp` 的策略

- `.tmp` 不属于有效预览片，任何检查都忽略它；
- 检测流程和全量检查都**不清理** `.tmp`；
- 插件启动时不扫描、不清理 `.tmp`；
- 正常成功、失败、取消，都由本次下载自己在 `finally` 中收尾；
- Emby 进程被强制终止或机器断电可能留下 `.tmp`，这是本方案接受的异常状态：它不会被识别为预览片，会在同一目标下次实际下载时被 `FileMode.Create` 覆盖。

因此现有的 `GenerateTrailersTask.CleanupOrphanTempFiles` 应当**删除**。

### 失败与兜底

本方案是**无状态**的：是否需要下载完全依据“本地是否存在有效预览片”，失败不留下任何痕迹，因此天然可重入。不需要失败记录表、不需要持久化重试计数、不需要启动时扫描恢复。

两种“没下到”的情况分别这样兜底：

| 情况 | 当次结果 | 兜底方式 |
|---|---|---|
| 本身没有预览片（`TrailerUrl` 为空） | 第三步结束，不下载，不产生文件 | `TrailerUrl` 属于元数据，只有重新刮削才可能变化。用户刷新该片元数据即触发 `ItemUpdated` → 自动重查；或运行一次全量检查 |
| 有 URL 但下载失败 | 重试耗尽后放弃，正式文件不出现，`.tmp` 已删除，本地仍判定为“缺失” | 下一次任何入口检查到它都会重新下载：用户刷新该片元数据，或运行一次全量检查 |

插件在重试耗尽后就放弃，不做任何后续安排：不排队重试、不记录失败项、不自动重跑。之后由用户刷新该片元数据或手动运行一次全量检查来触发，插件不再介入。

大量老片长期没有预览片，每次全量检查都会重新检查它们，这是无害的（纯文件判断），不引入负缓存、不做永久跳过标记。用户若要永久排除某个目录，使用 `.ignore`。

唯一无法自愈的情况是假成功的文件落了盘——本地判定为“已存在”，任何重试都救不回来。这正是 §3.1 从源头不写入 HLS 地址、第七步做 `Content-Type` 与字节数校验的原因。

```text
                             │
                             ▼
          下载到 .tmp（拒绝 HLS、空闲超时、字节校验）
                             │ 失败 → 删除 .tmp，本地仍为“缺失”，下次重来
                             ▼ 成功
                     落盘前再次 Check()
                             │ 已存在 → 删除 .tmp，结束
                             ▼ 仍缺失
              删除 0 字节目标文件（若有）
                             │
                             ▼
            File.Move(overwrite: false) → 正式文件
                             │
                             ▼
           计划任务进度 +1（成功与失败同样计入）
```

## 8. 业务不变量

实现必须始终满足以下规则：

1. 没有有效 `TrailerUrl`，绝不下载。
2. `TrailerUrl` 只接受可直接下载的地址，HLS 地址不写入、不下载。
3. 本地存在有效预览片，绝不下载、绝不覆盖。
4. 自动检查与全量检查使用完全相同的检测逻辑和同一条队列。
5. 元数据刷新不代表必须重新下载，最终以本地文件是否存在为准。
6. 任何入口都不能绕过 `.ignore`。
7. 正式文件只有在下载和校验成功后才出现；下载失败不能留下会被误判为成功的正式文件。
8. `ItemUpdated` 处理器只做过滤和入队，不阻塞、不做文件 IO、不下载。
9. 队列按 `InternalId` 去重；插件内任意时刻最多运行一个预览片检查或下载流程，不使用额外的锁。
10. 目标文件名来自原视频文件名，不依赖 `item.Name`。
11. 一个电影目录只维护一个预览片。
12. 自动检查和全量检查都不清理 `.tmp`；`.tmp` 只由本次下载自己收尾，或在同一目标下次下载时被覆盖。
13. 只允许删除插件自己命名的 0 字节目标文件，其余文件一律不动。
14. 文件落盘后由 Emby 自行扫描识别，插件不主动触发元数据刷新，避免形成刷新循环。
15. 计划任务不设置默认触发器。
16. 检测流程是无副作用的纯函数，删除文件只发生在下载阶段。
17. 计划任务的进度分母是预检得出的待下载数，不是全库总数。
18. 失败不留痕：下载失败后本地状态与从未尝试过完全一致，任何入口再次检查都会重新下载。

## 9. 验收标准

1. 新电影完成 MetaTube 刮削并取得 URL 后，自动下载一次，无需等待计划任务。
2. 一次性放入多部新片，全部依次下载，不因前一部正在下载而丢弃后续。
3. 新电影没有 URL 或只有 HLS 地址时，不产生下载行为，也不产生任何文件。
4. 用户刷新已有 URL 且已有本地预览片的电影，不重复下载。
5. 用户刷新已有 URL 但本地预览片缺失的电影，自动补充下载。
6. 电影标题被翻译或用户改名后再次刷新，不产生第二份预览片。
7. 全量检查只下载本地缺失项。
8. `trailers` 目录中已有用户放置的视频时，不下载。
9. 主电影同目录已有合法 `*-trailer.*` 文件时，不下载。
10. 同目录下第二部电影，在目录已有预览片时不下载。
11. `.ignore` 存在时，自动检查和全量检查都不处理。
12. 远程 URL 变化但本地文件存在时，不覆盖。
13. 下载失败或取消后，不留下正式文件，后续检查仍能重新下载。
14. 正常成功、失败或取消后，不残留 `.tmp`。
15. 检查流程不删除 `.tmp`，也不会把 `.tmp` 判断为已有预览片。
16. Emby 被强制终止并留下 `.tmp` 时，插件启动不清理；同一目标下次下载会覆盖该文件并正常完成。
17. 大文件在慢速链路上只要持续有数据就不会被超时中断。
18. 停止计划任务后，队列清空、当前下载中止。
19. 全新安装时，“Generate Trailers”在 Emby 任务列表中没有触发器。
20. 全量检查的进度条分母是待下载数：库中 5000 部片仅 10 部缺预览片时，进度按 10 部推进，每完成一部前进 10%。
21. 全量检查结束时输出 `待下载 N，成功 X，失败 Y` 汇总，并列出失败的电影名与原因。
22. 某部电影下载失败后，再次运行全量检查时它仍会被列入待下载并重新尝试。
23. 某部电影原本没有 `TrailerUrl`，后端补齐后用户刷新其元数据，能自动触发下载。
